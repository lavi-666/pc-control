## 2. АНАЛИЗ УЯЗВИМОСТЕЙ И РЕАЛИЗОВАННЫЕ ИСПРАВЛЕНИЯ

### 2.1. Исправление кэширования `X-Request-Id` (Безопасность и идемпотентность)

#### Обнаруженные проблемы в исходном коде:
1. **Обход авторизации (Critical Auth Bypass):** В хуке `before_request` проверка кэша выполнялась до вызова `check_token()`. Если злоумышленник отправлял запрос с ранее использованным `X-Request-Id`, сервер возвращал закэшированный ответ авторизованного пользователя вместе с конфиденциальными данными без проверки прав.
2. **Загрязнение кэша между пользователями (Cross-User Cache Poisoning):** Ключом кэша являлся исключительно заголовок `req_id`. При наличии нескольких сессий запросы пользователей конфликтовали и перезаписывали результаты друг друга.
3. **Подмена полезной нагрузки (Payload Tampering):** При повторной отправке того же `X-Request-Id` с совершенно другим телом запроса сервер возвращал старый закэшированный результат первого действия.
4. **Коллизия эндпоинтов (Cross-Endpoint Collision):** Запрос на `/volume` с тем же ID возвращал результат запроса на `/action`.
5. **Состояние гонки (Race Condition):** Несколько параллельных запросов с одинаковым `X-Request-Id` успевали одновременно пройти в обработчик до записи результата в кэш.
6. **Утечка памяти (Memory Leak):** Словарь кэша рос бесконечно без ограничения количества записей.

#### Реализованное решение (`server.py`):
```python
class IdempotencyRecord:
    def __init__(self, token_hash: str, method: str, path: str, body_hash: str, req_id: str):
        self.token_hash = token_hash
        self.method = method
        self.path = path
        self.body_hash = body_hash
        self.req_id = req_id
        self.status = "IN_PROGRESS"  # IN_PROGRESS, COMPLETED, FAILED
        self.created_at = time.time()
        self.completed_at = 0.0
        self.response = None

_idempotency_cache: collections.OrderedDict[str, IdempotencyRecord] = collections.OrderedDict()
_idempotency_lock = threading.Lock()
_IDEMPOTENCY_MAX_ENTRIES = 300
_IDEMPOTENCY_TTL_SEC = 15.0

def _get_request_identity() -> str:
    if has_request_context():
        token = request.headers.get("X-Auth-Token") or request.cookies.get("pc_token") or get_auth_token() or ""
    else:
        token = get_auth_token() or "test_default"
    return hashlib.sha256(str(token).encode("utf-8")).hexdigest()[:16]
```

- **Привязка к личности:** Ключ формируется строго как `f"{token_hash}:{req_id}"`.
- **Обязательная аутентификация:** `check_token()` выполняется ДО обращения к кэшу. Неавторизованные запросы получают `401 Unauthorized` и не имеют доступа к кэшу.
- **Строгая проверка контекста:**
```python
if rec.method != method or rec.path != path or rec.body_hash != body_hash:
    return {
        "error": "conflict",
        "status": 409,
        "message": "Idempotency key reused with different request payload or target endpoint"
    }
```
- **Блокировка конкурентных запросов:** При обращении с тем же ID во время выполнения предыдущего запроса возвращается:
```python
elif rec.status == "IN_PROGRESS":
    return {
        "error": "in_progress",
        "status": 409,
        "message": "Operation with this request ID is currently being processed"
    }
```
- **Заголовок реплея:** При отдаче ответа из кэша выставляется HTTP-заголовок `X-Idempotent-Replay: 1`.
- **Ограничение ресурсов:** `_idempotency_cache.popitem(last=False)` при превышении 300 записей; удаление записей старше 15 секунд.

### 2.2. Усиление безопасности Android WebView

#### Обнаруженные проблемы:
- В `MainActivity.java` настройки WebView допускали чтение локальных файлов (`setAllowFileAccessFromFileURLs(true)`, `setAllowUniversalAccessFromFileURLs(true)`).
- Метод `WebChromeClient.onPermissionRequest` безоговорочно предоставлял все запрашиваемые веб-страницей системные разрешения любому Origin.
- Внутренние ссылки могли загружаться внутри приложения без ограничений доверенных хостов.

#### Реализованное решение (`MainActivity.java`):
1. **Защита файловой системы и ресурсов:**
```java
webSettings.setAllowFileAccess(false);
webSettings.setAllowFileAccessFromFileURLs(false);
webSettings.setAllowUniversalAccessFromFileURLs(false);
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.LOLLIPOP) {
    webSettings.setMixedContentMode(WebSettings.MIXED_CONTENT_NEVER_ALLOW);
}
```

2. **Защита разрешений WebRTC (`onPermissionRequest`):**
```java
@Override
public void onPermissionRequest(final PermissionRequest request) {
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.LOLLIPOP) {
        String origin = request.getOrigin() != null ? request.getOrigin().toString().toLowerCase() : "";
        boolean isTrusted = origin.startsWith("http://127.0.0.1")
                || origin.startsWith("http://localhost")
                || origin.startsWith("http://pccontrol.local")
                || (serverUrl != null && !serverUrl.isEmpty() && origin.startsWith(serverUrl.toLowerCase()));

        if (!isTrusted) {
            request.deny();
            return;
        }

        // Предоставляем только захват аудио для WebRTC-аудиомониторинга, блокируя доступ к камере
        List<String> grantedResources = new ArrayList<>();
        for (String res : request.getResources()) {
            if (PermissionRequest.RESOURCE_AUDIO_CAPTURE.equals(res)) {
                grantedResources.add(res);
            }
        }
        if (!grantedResources.isEmpty()) {
            request.grant(grantedResources.toArray(new String[0]));
        } else {
            request.deny();
        }
    }
}
```

3. **Ограничение навигации (`shouldOverrideUrlLoading`):**
Разрешена внутренняя навигация только по доверенному URL сервера PC Control. Все внешние ссылки открываются в системном браузере через `Intent(Intent.ACTION_VIEW)`.

### 2.3. Защита от повторного выполнения опасных команд при HTTP 401

#### Обнаруженные проблемы:
В `web/js/app.js` функция `apiFetch` при получении ответа `401 Unauthorized` открывала диалог ввода пароля, после чего автоматически выполняла сохранённый запрос повторно. Если пользователь инициировал перезагрузку, выключение ПК или принудительное завершение процесса в момент завершения сессии, ввод пароля приводил к немедленному выполнению деструктивной операции без повторного подтверждения. Также генерация nonces выполнялась через небезопасный `Math.random()`.

#### Реализованное решение (`web/js/app.js`):
1. **Криптографическая генерация `X-Request-Id`:**
```javascript
function generateRequestId() {
  if (window.crypto && typeof window.crypto.randomUUID === 'function') {
    return window.crypto.randomUUID();
  }
  if (window.crypto && window.crypto.getRandomValues) {
    const bytes = new Uint8Array(16);
    window.crypto.getRandomValues(bytes);
    return Array.from(bytes, b => b.toString(16).padStart(2, '0')).join('');
  }
  return 'req_' + Date.now() + '_' + Math.random().toString(36).substring(2, 12);
}
```

2. **Запрет автоматического реплея мутирующих запросов:**
```javascript
// Мутирующие команды (POST, PUT, DELETE, PATCH) ПРЕРЫВАЮТСЯ при 401 во избежание непреднамеренного выполнения опасных действий
if (isMutating) {
  showPasswordModal();
  throw new Error('Сессия авторизации завершена. Пожалуйста, введите пароль и повторите действие.');
}
// Только безопасные запросы чтения (GET, HEAD) могут быть автоматически повторены
```

### 2.4. Устранение гонок и падений Android MediaCodec

#### Обнаруженные проблемы:
1. Вызов `stopStream()` из UI-потока вызывал `releaseDecoder()` немедленно, в то время как фоновый поток `pc-native-stream-worker` находился в цикле вызова `decoder.dequeueOutputBuffer()` или `feedDecoderFrame()`. Это приводило к исключению `IllegalStateException` и нативным сбоям Android Media Server.
2. При сворачивании приложения или повороте экрана `surfaceDestroyed()` обнулял `SurfaceHolder`, но декодер продолжал попытки отрисовки `decoder.releaseOutputBuffer(outIndex, true)`, что вызывало краш графического конвейера.

#### Реализованное решение (`NativeScreenView.java`):
1. **Синхронизация через `decoderLock`:**
Все операции с декодером (`initDecoder`, `feedDecoderFrame`, `feedDecoderNalu`, `drainOutputBuffers`, `releaseDecoder`) защищены общим мьютексом:
```java
private final Object decoderLock = new Object();
```

2. **Корректный порядок завершения потока в `stopStream()`:**
```java
public void stopStream() {
    isStreaming.set(false);
    mainHandler.removeCallbacks(hideControlsRunnable);
    mainHandler.removeCallbacks(diagUpdateRunnable);

    synchronized (surfaceLock) {
        surfaceLock.notifyAll();
    }

    HttpURLConnection conn = activeConn;
    if (conn != null) {
        try { conn.disconnect(); } catch (Exception ignored) {}
        activeConn = null;
    }

    Thread wt = workerThread;
    if (wt != null) {
        wt.interrupt();
        try {
            wt.join(600); // Ожидаем завершения сетевого цикла
        } catch (InterruptedException ignored) {}
        workerThread = null;
    }

    releaseDecoder(); // Безопасное освобождение без параллельных вызовов
    ...
}
```

3. **Безопасная выгрузка буферов:**
```java
boolean canRender = false;
synchronized (surfaceLock) {
    canRender = surfaceReady && surfaceHolder != null && surfaceHolder.getSurface() != null && surfaceHolder.getSurface().isValid();
}
// Рендерим кадр на Surface только если поверхность валидна, иначе освобождаем буфер без рендеринга
decoder.releaseOutputBuffer(outIndex, canRender);
```

### 2.6. Дизайн, Letterbox-масштабирование и стабилизация FPS

1. **Пропорциональное масштабирование (Fit Center / Letterbox):**
В переопределенном методе `onMeasure` рассчитывается точное соотношение сторон видеопотока (16:9). При отображении на ультрашироких экранах (19.5:9, 20:9) SurfaceView центрируется с добавлением Pillarbox-полос по бокам. Видео больше не растягивается по горизонтали. 2. **Истинный Fullscreen:**
Реализован через `WindowInsetsControllerCompat` с флагом `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE` и `LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES`.
3. **Плавный автоскрываемый интерфейс:**
Плавающий полупрозрачный тулбар PC Control с анимацией затухания и автоскрытием через 3.5 секунды после касания.
4. **Устранение джиттера FPS:**
   - Высокоточный `FpsTracker` на кольцевом буфере с окном 1500 мс исключает мгновенные скачки счётчика.
   - На сервере в `modules/streaming.py` подключён Windows таймер высокой точности `timeBeginPeriod(1)` и drift-компенсирующий планировщик кадров, удерживающий стабильные 60.0 FPS.
