# 14. Полный аудит кода: архитектура, баги, стабильность, производительность

Версия APK: **13 (2.3.6)**, подпись v2/v3 прежним ключом (SHA-256 `9e0792b4…983e13`).
На телефоне не проверялось. Каждая находка ниже **воспроизведена** на этом ПК
(рабочий сервер или его копия). Исправление проверено повторным замером и регрессионным тестом.

## Как проверялось

- **Статический анализ:**
  - Python: `pyflakes` по `server.py`, `modules`, `core`, `scripts`.
  - Java: `javac -Xlint:all` по всем исходникам Android.
  - Веб-интерфейс: в настоящем Chrome (тест `tests/test_web_ui_browser.py`).
- **Динамика на живом сервере:**
  - журнал ошибок и журнал действий;
  - TCP-соединения;
  - число потоков, дескрипторов и памяти во времени.
- **Изоляция причин:**
  - копия сервера в отдельном процессе;
  - по одному маршруту и по одной подсистеме за раз;
  - определение DLL, создающей потоки (адрес старта потока).
- **Тесты:** полный `pytest`, 187 из 187 (было 182 + 3 падающих). Новый файл
  `tests/test_audit_regressions.py`: на старом коде его тесты падают, на новом проходят.

## Найдено и исправлено

### Безопасность

| # | Проблема | Подтверждение | Исправление |
|---|---|---|---|
| S1 | **Доступ к ПК без пароля из локальной сети.** `/api/pair/ticket` выдавал билет любому адресу LAN/Tailscale, а `/api/pair/exchange` меняет билет на сам пароль | С адреса 192.168.0.101 двумя запросами без пароля получен настоящий пароль | Билет выдаётся только с действующим паролем |
| S2 | **Пароль в журнале открытым текстом.** Видео и звук передают `?token=…`, werkzeug писал адреса в `logs/server_stderr.log` | 10 строк с паролем в журнале | Фильтр журнала маскирует `token=`/`ticket=`; в существующих журналах пароль заменён на `***` |

### Ошибки

| # | Проблема | Последствие | Исправление |
|---|---|---|---|
| B1 | В `modules/system.py` используется `psutil`, но нет `import` | «Завершить процесс» **всегда** возвращал 500. Список процессов шёл медленным путём через `tasklist`, без защиты от повторного использования PID | Добавлен импорт |
| B2 | **Звук ПК в APK не работал.** `/audio` проксировался во внешний `tools/streamer.exe`: первый байт приходил через 6–10+ с, стример копил зависшие соединения | 0 байт за 10 с, обрыв. Телефон переподключался каждые 12 с (в журнале 14 ошибок `rust_audio_proxy`) | Встроенный захват WASAPI loopback: первые данные через 0,1 с, 186 КБ/с (реальное время). Rust-путь только по флагу `PC_CONTROL_RUST_AUDIO=1` |
| B3 | Нативный плеер считал звук всегда 48 кГц стерео и не читал заголовок WAV | На ПК со звуковой картой 44,1 кГц звук шёл бы с неправильной скоростью | Частота и число каналов берутся из заголовка WAV, `AudioTrack` создаётся под них |
| B4 | Панель управления создавала билет «Открыть веб-пульт» в своём процессе, а погасить его может только сервер | Веб-пульт открывался с недействительным билетом | Билет запрашивается у сервера по HTTP с паролем |
| B5 | `_ensure_rust_streamer` при медленном ответе стримера запускал **второй** экземпляр, дескриптор прежнего терялся | Лишние процессы `streamer.exe` | Занятый порт или живой процесс означает «уже запущен» |

### Стабильность и производительность

| # | Проблема | Замер до → после | Исправление |
|---|---|---|---|
| P1 | `/audio` и `/api/mic/*` создавали и уничтожали PortAudio на каждый запрос, при обрыве клиента оставались потоки ОС | 10 переподключений: 15 → 42 потока; после исправления 17 → 17 | Один общий экземпляр PortAudio на процесс со счётчиком активных потоков. Пересоздаётся только без активных потоков, чтобы увидеть смену устройства |
| P2 | Нарушения правил COM в UIA/pycaw: `CoUninitialize` вызывался, пока COM-объекты ещё живы; новый `CUIAutomation` на каждое чтение вкладки (раз в 0,85 с); `IAccessible` от `AccessibleObjectFromWindow` не освобождался | Источник висящих рабочих потоков | COM инициализируется один раз на поток. Один `IUIAutomation` на поток (рекомендация Microsoft). Медиамонитор в MTA. `IAccessible` освобождается |
| P3 | Если вкладка YouTube Music не найдена, полный обход дерева доступности Chrome (`FindAll` по всем потомкам + «будильник» MSAA) шёл каждые 0,85 с | ~10 % CPU в простое | После неудачи следующая попытка через 5 с |
| P4 | Журналы росли без ограничений, `/history` читал `actions_log.jsonl` (1,2 МБ) целиком | Рост диска и времени ответа | Ротация: действия ≤ 2 МБ, ошибки ≤ 1 МБ, хранится свежая половина, обрезка по границе строки |
| P5 | Сторож ресурсов | — | Раз в минуту проверяет число потоков. От 400 пишет предупреждение в журнал, от 1500 перезапускает сервер через watchdog, **только когда никто не подключён** |

**Рост потоков сервера: что осталось неясным.** Рабочий сервер дорастал до 779 потоков,
это рабочие потоки системного пула Windows (старт в `ntdll.dll`). Рост шёл **эпизодами** и
одновременно во всех процессах с медиамонитором, в том числе в копиях сервера, к которым
не было ни одного запроса. Значит, его включает внешнее состояние Chrome/YouTube Music. Вне
эпизода ни одна подсистема по отдельности потоки не теряет, поэтому точный вызов Windows,
оставляющий поток, повторно воспроизвести не удалось. Исправлены все найденные нарушения
COM (P2), снижена частота обращений к Chrome (P3), добавлен сторож (P5). Итог 20-минутной
трассировки — в разделе ниже.

### Тесты

- **Три теста деинсталлятора были не просто «падающими», а опасными.** Они запускали
  настоящий `Uninstall.exe` без песочницы. Тот запрашивал права администратора (UAC) и после
  согласия мог откатить **реальные** системные настройки PC Control на этом ПК (правила
  брандмауэра, Wake-on-LAN). Тесты переведены на `--sandbox-dir`: те же проверки файлов, все
  системные операции имитируются. Тесты проходят.
- Тест деинсталлятора больше не перезаписывает `Uninstall.exe` в корне проекта (файл под git),
  а собирает его во временную папку.
- `Tuple` импортирован в двух модулях лаунчера (сейчас безвреден из-за `__future__`).

## Проверено, проблем нет

- Сторожевой процесс работает в одном экземпляре (защита мьютексом).
- Панель управления слушает только `127.0.0.1` и проверяет Host/Origin (защита от DNS-rebinding).
- `shell=True` есть только в неиспользуемой функции панели. `eval`/`exec`/`pickle` нет.
- Java: кроме предупреждений об устаревших API (они нужны для Android 7+), предупреждений нет.
- Видеопоток при 15 переподключениях подряд не теряет потоки и дескрипторы.
- Опросы веб-пульта адаптивные и останавливаются при свёрнутом приложении.

## Не исправлено (рекомендации)

- `modules/media.py` дублирует глобальные переменные `modules/media_queue.py` и синхронизирует
  их вручную. Сейчас код читает актуальные значения через `_mq.…`, ошибки нет, но схема хрупкая.
  Не переделывал: высокий риск сломать очередь YouTube Music.
- Часть старых тестов (`tests/test_batch_*.py`) работает с **рабочим** сервером: ставит на паузу
  и включает музыку пользователя, меняет и возвращает пароль. Лучше перевести их на копию
  сервера в тестовом режиме.
- `/status`, `/api/qr`, `/api/lan_info` без пароля отдают имя ПК и адреса устройствам локальной
  сети. Риск низкий, оставлено ради сопряжения по QR.
- Нативный плеер Android (панель настроек) пока только на русском.
